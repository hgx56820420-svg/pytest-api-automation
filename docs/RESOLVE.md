# RESOLVE：重大问题复盘记录

> 本文记录两个动摇框架可信度的核心问题的完整复盘：出现原因、故障点、
> 解决方法与防复发约定。同类问题再出现时，先来这里对照。

---

## RESOLVE-001：破坏性契约变化被框架"静默消化"，服务端误删接口不报警

### 问题现象

被测服务**误删了支付/扣款接口**（典型回归事故）后，测试框架的完整表现是：

1. 运行时 OpenAPI 里少了这个接口；
2. 框架把契约基线**替换成"删完之后"的版本**，并做选择性再生；
3. 被删接口的用例不再生成，剩余用例全部通过；
4. `execution-report.json` 的 `contract_status` 显示 `compatible`，最终决策 **PASS**，CI 绿；
5. 上线后才发现接口没了——资损。

唯一的痕迹是 `repair-history.json` 里一条 `contract_breaking_change` 记录，
但 CI 门禁不读它，等于没人看见。

### 出现原因

选择性再生能力（roadmap V2："契约变化后只重新生成受影响的用例和脚本"）
在设计时把"恢复覆盖"放在了"变更透明度"之上，三个环节叠加造成静默：

1. **基线被覆写**：再生节点直接把 `normalized-requirement.json` 覆写为当前
   运行时契约——"接受漂移"成了默认动作，没有任何人工确认节点；
2. **门禁自我失效**：基线覆写后，契约门禁再比对自然 `compatible`，
   破坏性历史从门禁视野中消失；
3. **决策不含历史**：最终决策只看当次比对结果与用例断言，不关心
   "这一轮曾经发生过 breaking"；执行报告的 `contract_status` 同样只反映
   最后一次比对。

本质：**把"框架能适应变化"错当成了"变化不需要人知道"**。roadmap 自己的
底线（"破坏性契约变化应阻断旧脚本执行"）被再生能力绕过了。

### 故障点（代码位置）

| 位置 | 故障行为 |
|---|---|
| `workflow.py` `contract_gate` breaking 分支 | 直接 `route=regenerate`，无任何升级动作 |
| `workflow.py` `regenerate_affected` | 覆写 `normalized-requirement.json` 为 runtime，且不标记本轮发生过 breaking |
| `workflow.py` `finalize` | 决策只看 `result-review` 与当轮 escalation，breaking 历史不影响决策 |
| `reporting.py` `build_execution_report` | `contract_status` 取最后一次门禁结果，breaking 被覆盖 |

### 解决方法（commit `a4698d7`）

破坏性契约变化的处理流程改为：

```text
检测到 breaking
  → 升级节点（escalate）：本轮记录"契约变更需人工确认"
  → 选择性再生照常执行（再生能力保留，用例不裸奔）
  → 本轮最终决策强制 NEEDS_HUMAN（即使所有用例通过）
  → 人工确认此次契约变更是预期行为后，以当前契约为基线重跑一轮
  → 基线与运行时一致 → 门禁 compatible 且无升级 → 恢复 PASS
```

关键点：**PASS 的恢复必须以"人工确认 + 以新契约重跑"为前提**，
误删接口的那一轮 CI 必然是红的。

回归保护：`tests/test_agent_v2.py::test_workflow_escalates_breaking_contract_until_human_confirms`
覆盖两段行为——变更轮 NEEDS_HUMAN + 升级留痕，确认轮恢复 PASS。

### 防复发约定

1. **任何"框架自动适应变化"的路径，终点必须是人工可见的决策降级**，
   不允许适应过程静默完成；
2. 契约基线只能被"人工确认后的重跑"替换，不能被再生动作直接替换；
3. 新增任何自动再生/自愈能力时，必须在 `finalize` 决策中显式声明其痕迹。

## RESOLVE-002：新接口没有用例，用例只覆盖"预写过脚本的接口"

### 问题现象

adapter 的场景映射是人工预写的（为每个接口手写业务场景与数据库断言）。
服务**新增一个接口**后：

1. 用例生成完全不认识它（标记 `unsupported`）；
2. 不产生任何用例，新接口零测试覆盖；
3. 覆盖审核还会把整轮工作流卡成 NEEDS_HUMAN（且修复回路无法自愈）。

### 出现原因

用例生成能力与 adapter 的预写映射**强绑定**：`plan_cases` 只为
`adapter.scenarios` 里登记过的 operation 生成用例。覆盖审核对"覆盖"的
定义也是"预写场景是否齐全"，而不是"契约里的接口是否都有测试"。

本质：**框架把"人工写过深场景"当成了覆盖的必要条件**，缺少一个不依赖
人工的兜底生成层。接入第 2、3 个被测对象时暴露的各种问题都是"预写能力
不足"，但"新接口出现"这个最常见的变化反而没有任何兜底。

### 故障点（代码位置）

| 位置 | 故障行为 |
|---|---|
| `planner.py` `plan_cases` | 只按 `adapter.scenarios` 生成，未映射的 operation 直接跳过 |
| `planner.py` `review_coverage` | 把文档检测到的场景缺口一律视为阻塞（跨领域措辞也会误卡）；对"operation 无任何用例"只报 `unsupported` 不产生用例 |
| `executor.py` | 没有任何 schema 驱动的通用请求构造能力 |

### 解决方法（commit `a4698d7`）

新增 **schema 驱动的通用契约冒烟用例层**（`generic.*` 用例）：

1. **生成**：adapter 未预写场景的每个 operation 自动生成一条冒烟用例
   （`planner._generic_case`），期望状态码 = 该接口文档声明的全部状态码；
2. **执行**（`executor._scenario_generic`）：
   - 请求由 OpenAPI schema 确定性构造：必填字段、minLength/maxLength、
     enum、minimum/exclusiveMinimum、path/query 参数，绝不使用随机值；
   - 接口要求认证时先注册登录再携带 Bearer Token；
   - 状态码判定：**拒绝 5xx / 3xx / 未声明状态码**；容忍数据依赖的 4xx
     （重要发现：FastAPI 不会把 `HTTPException` 产生的 401/404 写进
     OpenAPI，schema 合法的请求命中它们属于正常数据依赖）；
   - 2xx 响应必须通过契约结构校验（jsonschema 对 OpenAPI 声明）；
3. **审核**：覆盖审核的场景缺口检查只对 adapter 声明过能力的场景报警，
   跨领域措辞噪音不再误卡流程；"generic" 场景在执行器基类上有实现，
   通过 handler 存在性审核。

验证：单元测试（生成/覆盖/工作流三层）+ 真实服务验证——对运行中的
Mini Shop 以"零预写场景"adapter 执行全部 22 个接口的通用冒烟用例，
**22/22 通过**（含需认证接口、schema 构造请求体、401/404 数据依赖容忍）。

职责边界（重要）：**通用冒烟只保证"接口存在、不 5xx、响应符合契约"，
不保证业务语义**——语义回归（扣错钱、状态机漏洞）仍由预写业务场景负责。
两层关系：冒烟层管"新接口不裸奔"，业务层管"资金与状态安全"。

### 防复发约定

1. 新接口合入的同一轮 CI 里必须出现它的 `generic.*` 用例——覆盖审核已经
   不再可能对未知接口报 approved（要么有业务用例，要么有冒烟用例）；
2. 预写业务场景是**增强**而非**前提**：adapter 作者按资金/状态风险决定
   哪些接口值得手写深场景；
3. 通用请求构造器只允许确定性取值（禁随机），保证可复现与可审计。
